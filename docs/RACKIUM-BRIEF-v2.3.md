## 3. Product and scope

Rackium is a standalone, multi-tenant web platform that runs a network infrastructure project from existing-inventory validation to client handover on one shared data model. Tagline: **Infra, Clearly Connected.**

**Core principle.** Every drawn object is a data record. A connection drawn once feeds the cable schedule, BOM, deployment checklist, CMDB and handover documents. Nothing is re-typed between phases. \[v2.2 Executive Summary, Product Principles\]

**The nine phases, in order:**

1. CMO Inventory Validation
2. Physical Site Survey
3. HLD (High-Level Design)
4. LLD (Low-Level Design)
5. Solution Package
6. BOM
7. Deployment & Installation
8. CMDB
9. Handover

A phase cannot start until its predecessor is submitted, and cannot complete until its predecessor is approved. A PM may explicitly allow phases to run in parallel per building. The draft BOM is the exception: it is live from HLD onward (D18).

**NexAI.** A product name for Rackium's built-in rule-based logic, not a separate module and not machine learning. It covers: cable length suggestion, optic and accessory suggestion, equipment best-fit ranking, validation rules, HLD suggestion from blueprint templates plus survey data, BOM generation and quantity reconciliation, design-vs-deployment deviation detection, CMDB reconciliation, Solution Package readiness checks, DGUV expiry calculation and naming enforcement. The label "AI computer vision" and confidence percentages shown in the renders are not used.

**In scope.** Everything specified in v2.2 as amended by this document, including: blueprint templates, logical topology objects, custom validation rules builder, version control and diff, notifications and task assignment, audit trail, document generation, DGUV tracking, QR cable label generation, floor-plan upload and pathway map, global search, Project Management Suite \[v2.2 §21\], real-time presence and port locking, and "already-open" offline survey. The development team sets the build sequence.

**Build order set by the client:** main dashboard UI first, then the Rackium Editor, then the rack elevation.

**Not part of this build (deferred):**

| Item | What happens instead |
| --- | --- |
| OCR, computer vision, photo-based rack capture | Manual placement with validation; photos stored as evidence |
| Machine-learning suggestions (HLD, Solution Package) | Rule-based suggestions from blueprint templates and survey data |
| Camera barcode / QR scanning | Manual entry of serial and MAC, validated against CMO |
| Full installable offline app (PWA) | "Already-open" offline mode (D10) |
| Visio .vssx stencil import | SVG/PNG stencil import |
| Merging design branches | Branch, then promote or discard |
| Client login / Client Viewer role | Share-link approvals (D03) |
| Automatic port assignment | Architect assigns; system suggests available ports |
| Custom survey fields feeding calculations | Custom fields are stored and exported only |
| Automatic SERVON catalogue sync | Manual flag (D35) |

**Out of scope entirely:** \[v2.2 §15\] still applies, except that pricing (D19), offline survey (D10), QR labels and floor-plan upload are now in scope.

## 4. Data model, roles and statuses

### 4.1 Hierarchy

**Organisation → Project → Country → SAL code → Campus → Building → Wing (optional) → Floor → Room → Rack → Device → Port**

Example: Technonex / LANspire / DE / ERL / C01 / B001 / EG / TR-EG-01 / R01.

- Every record belongs to exactly one organisation. Organisation isolation is enforced on the server for every read and write; no API call returns another organisation's data.
- **Who creates what:** Org Admin or PM creates projects; PM creates Country → Building; PM or Architect may pre-create floors, rooms and racks (e.g. from a floor plan); Field Engineers create or confirm them in the survey Site Structure step; the Architect verifies. *(Proposed)*
- Device roles, connection schema and catalogue fields follow \[v2.2 §2.2–2.4\] with the changes in §6.

**Rack placement rules** (Client, Q28):

- Devices are tracked by RU position and mounting face (front or rear). A front device and a rear device may share an RU.
- A catalogue item flagged `full_depth` occupies the RU on both faces. *(Proposed)*
- 0U items (vertical PDUs) do not occupy RUs; they are recorded against the rack's left or right rear mounting position.
- RU states: **free, occupied, reserved, blocked**. Reserved is set by the Architect (e.g. "Reserved for FMO") and can be released. Blocked is set by PM or Org Admin (physically unusable); the Architect cannot override it.
- Rack heights: 12, 24, 42, 45, 48U, plus custom heights defined by the Org Admin (e.g. 23U, as found in the Siemens survey).

### 4.2 Standard examples

Hostname: `E-DE-ERL-C01-B001-EG-001` (role · country · SAL · campus · building · floor · sequence). Details in §6.6.

## 5. Module specifications

Each module follows v2.2 unless a rule below changes it.

### 5.1 CMO Inventory Validation \[v2.2 §3.5, §20.2\]

- CMO is imported from Excel and scoped per building. The dashboard shows CMO status per building.
- Devices with no building go to an **Unassigned** list at SAL level. The PM assigns them. Each unassigned device counts as an open blocker.
- During the survey, each scanned or typed serial/MAC is marked Validated (found in CMO), Not in CMO, or Duplicate (already used elsewhere in the project).

### 5.2 Physical Site Survey \[v2.2 §3.5\]

**Flow:** Site Structure → Room Details → Rack Survey → Existing Connectivity / Building Connections → Validation.

**Forms.** 18 fixed tabs based on the Siemens Physical Site Survey workbook: Location Details, Floor-wise Device Details, Rack Layout, Comms Rooms Summary, Fibre Cabling, Passive Copper Cabling, WAN, WLAN, SSID, Firewall, Lab / Isolated Network, Local Server, Endpoint, BMS & rVLAN Device Inventory, Storage Area, Rooms and Open Areas, Reference Images, Passive Requirements for FMO.

- Field names and the Must / Good-to-have marking come from the workbook.
- Core fields cannot be removed or renamed. Organisations may add custom fields; these are stored and exported but do not feed calculations.
- **Building-level tabs** (Location, WAN, SSID, Storage Area, Passive Requirements for FMO) are submitted and verified once per building. All other tabs are per room.
- A building's survey is complete when every room tab and every building tab is Verified.

**Rack Survey (manual, no photo recognition):**

1. Engineer uploads rack photos: front, rear, PDU/UPS. Photos are evidence only.
2. Engineer drags objects from the library onto the front or rear elevation at the correct RU, or picks a device from the room's CMO list.
3. System validates: RU overlap per face, object height vs free RU, rack boundary, serial/MAC against CMO, required photos present, PDU socket counts.
4. System calculates the readiness summary: available RU, contiguous free RU, depth compatibility, power readiness, cable management, mounting material.
5. Engineer confirms; the rack is submitted with the room for Architect verification.

**Rack library:** 24-port patch panel, 48-port patch panel, fibre patch panel, 24-port switch, 48-port switch, chassis switch, firewall, cable manager, PDU (0U and 1U), UPS, shelf, blanking panel, brush panel, KVM tray, fan unit, other accessory. Items link to catalogue models where available; generic items are allowed.

**Offline ("already-open" mode):** a survey opened online keeps working offline, including photos, and syncs automatically on reconnect. If two people saved the same record, the last save wins and the sync screen shows what changed and who made the conflicting edit.

### 5.3 HLD \[v2.2 §3.6\]

- Canvas, object library, toolbar, CMO overlay, logical topology, blueprint templates and annotations as in v2.2.
- **NexAI-suggested HLD** = the selected blueprint template filled with the verified survey's rooms, racks and pathways. The architect reviews and edits it.
- Edit Uplink sets endpoints, required speed, medium and SFP. Port selection is optional in HLD and mandatory in LLD.
- HLD approval by Reviewer or PM (D06).

### 5.4 LLD and Rackium Editor \[v2.2 §3.7, §14\]

- LLD derives from the latest approved HLD.
- **Rack elevation:** the Architect places devices manually. The system validates RU overlap, rack height, power and weight; it does not auto-assign positions.
- **Port mapping:** the Architect assigns ports. The system suggests available, compatible ports and naming; it never auto-assigns.
- **Rackium Editor** is a mode inside LLD for port-level mapping. The same editor is reused, read-only or in capture mode, in the Survey rack view and in Deployment.
- LLD defines the designed connection, including patch-panel hops. Horizontal cabling to outlets and AP drops may stay TBD in LLD; Field Engineers capture it in Deployment.
- Cable IDs are assigned at LLD so labels can be printed before installation.
- **HLD changed after LLD:** the LLD is flagged "based on HLD v\[n\]", conflict warnings appear, and a side-by-side HLD vs LLD reconciliation view shows the differences. The Architect updates manually or starts a new LLD version.

**Bill of Resources** = the installation work generated from the design, per building, floor and room:

- Task lines with quantities: install device, mount AP, install rack/accessory, patch copper cable, patch fibre cable, label cable, test link, DGUV inspection.
- Role per task (e.g. Field Engineer).

- No labour cost.
- The same task list becomes the Deployment checklist.

- PM generates a link with a password and an expiry (default 14 days, 1–30 allowed). *(Proposed)*

- Approval freezes HLD and LLD. Later changes require a change request \[v2.2 §3.7A.6\].

### 5.6 BOM \[v2.2 §3.8\]

- **Draft BOM** is generated live from HLD onward and updates as the design changes. It shows the sub-label "Draft".
- After Solution Package approval, the BOM becomes the procurement BOM and procurement status fields unlock. The PM approves the procurement BOM and updates procurement status.
- Each line keeps its source tag (Survey, HLD, LLD) and a vendor field. Partial vendor packages are not built.
- **Pricing:** unit price comes from the catalogue (entered by PM or Org Admin). Line total = price × quantity. PM sets a margin %. Visibility per §4.3. Currency per organisation, default EUR.
- Cables are listed at their selected stock lengths (§6.3). Power cords are selected automatically (§6.7).

### 5.7 Deployment & Installation \[v2.2 §3.9\]

- A device can be installed as soon as its materials are marked Delivered; the phase does not wait for the full BOM.
- Per-device checklist, evidence photos and exceptions as in v2.2. Serial and MAC are entered manually and validated (§5.1).
- Field Engineers record the actual patching against the read-only LLD. Any difference from the design (media, SFP, port, RU, cable ID) is flagged as a deviation and must be resolved or logged as an exception.
- Deployment screens are fully usable on phones.

### 5.8 CMDB \[v2.2 §3.10\]

- The CMDB is the as-built record. Architects and PMs may make operational edits, flagged "operational change" (vs "design intent") in the audit trail.
- **Port click** highlights: the port, the routed cable in its media colour, the route through cable managers, the patch-panel ports, every cable ID, source and destination, test result and installation status.
- Trace example: Edge 04 Te1/1/1 → Cable 26184735 → PP-02 Port 08 → Cable 26184736 → PP-01 Port 24 → Cable 26184737 → Border Te1/1/4.
- Cable routes are drawn orthogonally and bundled; no diagonal lines. Access ports never exceed the device's real port count (e.g. Gi1/0/48 on a 48-port switch; uplink module ports are listed separately).

### 5.9 Handover \[v2.2 §3.11\]

- The 11-document handover package from v2.2 applies.
- Client sign-off uses the same share-link mechanism as the Solution Package.
- On acceptance the project version is frozen as an immutable baseline. Design phases become read-only; a new cycle starts from this baseline.

## 6. Cross-cutting rules

### 6.1 Cable ID

| Rule | Value |
| --- | --- |
| Format | Free text, 1–32 characters, leading and trailing spaces removed |
| Default | System suggests the next free 8-digit number (e.g. 26184735); user can accept or type their own |
| Uniqueness | Unique per project, case-insensitive, across connection IDs and hop segment IDs |
| Assigned | At LLD, so labels can be printed before installation |
| Existing cables | Surveyed cables keep their existing marker (e.g. "D6"); no forced renumbering |
| Both ends | Both ends of a cable carry the same ID |
| Logical link IDs | Design labels such as UL-05 may exist but never replace a Cable ID |

### 6.2 Connection model

One connection record per end-to-end link:

- Source device and port; destination device and port.
- Media type, speed, source SFP, destination SFP.
- **Cable ID** (mandatory once LLD is approved).
- Ordered **hops**: each hop has patch panel, incoming port, outgoing port, location (room, rack, RU) and an optional **segment Cable ID**.
- Three lengths (§6.3), status (§4.4), test result, evidence.

The trace view lists every hop and every cable ID in order. When segment IDs are used, the connection Cable ID is shown first. Remaining fields as in \[v2.2 §2.3\].

### 6.3 Cable length

Each connection carries three lengths: **Suggested** (calculated by the system), **Engineer Selected** (set in LLD, defaults to Suggested) and **Installed** (recorded in Deployment). The BOM uses Engineer Selected.

**Same rack:**

```latex
L = |RU_{source} - RU_{dest}| \times 0.045\,\text{m} + 0.5\,\text{m}
```

**Same room, different racks:**

```latex
L = 0.8\,\text{m} \times |\text{rack position}_{source} - \text{rack position}_{dest}| + 1.5\,\text{m} + 1\,\text{m}
```

**Different rooms or floors:**

```latex
L = \text{surveyed pathway length} + 2\,\text{m}
```

If no pathway is surveyed, the Architect enters an estimated length. The connection is marked "Estimated" and raises the Info finding "Cable pathway not surveyed".

The calculated value is **rounded up** to the next stock length for that media and situation. If it exceeds the longest stock length, a Warning "Custom length required" is raised. Rack spacing (0.8 m), vertical routing (1.5 m) and slack values are project settings.

Worked examples: RU40 to RU42 in one rack = 0.59 m → **1 m**. Neighbouring racks in one room = 3.3 m → **5 m**. The allowance method in \[v2.2 §14.4 and §19.4\] is removed.

**Stock lengths** (configurable by Org Admin):

| Media / situation | Lengths (m) |
| --- | --- |
| Cat6A, same rack | 0.3, 0.5, 1, 1.5, 2, 3 |
| Cat6A, same room | 3, 5, 7, 10, 15 |
| Cat6A, between rooms | 15, 20, 30, 50, 75, 90 |
| OS2 single-mode fibre | 5, 10, 15, 30, 50, 100, 200, 500 |
| OM4 multimode fibre | 3, 5, 10, 15, 30, 50, 100 |
| DAC | 1, 2, 3, 5 |
| Stack cable | 0.5, 1, 3 |

### 6.4 Media length limits

The limit for a connection is the reach of its selected optic in the catalogue. Where no optic applies, defaults are (editable in project settings):

| Media | Default limit |
| --- | --- |
| Cat6A copper | 100 m channel |
| OM4 multimode (10G-SR) | 400 m |
| OS2 single-mode (10G-LR) | 10 km |
| DAC, stack cable | The product's fixed length |

### 6.5 Catalogue \[v2.2 §2.4, §6\]

- Technonex supplies catalogue data, starting with 20–30 Cisco Catalyst models and growing to 200–300, from vendor datasheets. EOS/EOL dates from vendor lifecycle pages.
- Development builds the data structure, admin UI and CSV import.
- Fields added to v2.2: unit price and currency, `full_depth` flag, mounting (front / rear / 0U), front and rear artwork, optic reach (m), power inlet type (e.g. C14, C20), `servon_available` flag and SERVON product code (manual, no sync).
- Categories include probe devices (e.g. ThousandEyes).
- Until final artwork is supplied, devices render as simplified rectangles with the correct port count and exact sequential numbering. Port numbering must always be exact: no skipped, duplicated or extra ports. The supplied SERVON 24-port panel drawing is used as-is.

### 6.6 Naming convention \[v2.2 §20.10\]

- Default pattern: `{role}-{country}-{sal}-{campus}-{building}-{floor}-{seq}`, e.g. `E-DE-ERL-C01-B001-EG-001`.
- Role codes: F = Fusion, B = Border, D = Distribution, E = Edge, A = Access point.
- Floor tokens: FU1 (basement), EG (ground), 1.OG, 2.OG, 3.OG. Configurable per project (e.g. F00, F01).
- Characters not valid in hostnames (dots, spaces) are removed when the name is built: floor 1.OG becomes `1OG` in the hostname. *(Proposed)*
- Sequence: 3 digits per role per floor.

### 6.7 Power cords

The BOM selects each power cord automatically, in this order:

1. **Customer standard** set by the PM for the project (e.g. "2 m C13/C14, black") overrides everything.
2. **Plugged into a PDU:** PDU socket decides the cord (C13 socket → C13/C14 cord; C19 socket → C19/C20 cord), matched to the device inlet.
3. **Direct wall socket:** country plug table (e.g. DE → Schuko to C13). Technonex supplies the table (about 15 rows).

Default cord length is an organisation setting (2 m unless changed).

### 6.8 Validation engine \[v2.2 §5\]

VAL-001 to VAL-010 and all listed Critical, Warning and Info rules apply, with these changes:

| Change | Rule |
| --- | --- |
| Added | VAL-011, Critical: cable length exceeds the media or optic limit (§6.4) |
| Added | VAL-012, Warning: no stock cable length long enough; custom length required |
| Added | VAL-013, Critical: duplicate Cable ID in project |
| Changed | "UPS cannot carry the full rack load" and power budget use catalogue power draw vs PDU/UPS capacity |
| Disabled | "Cooling capacity approaching thermal load" until Technonex supplies thermal limits |

### 6.9 DGUV \[v2.2 §20.9\]

- Inspection interval 48 months. Status: Valid; Expiring soon (≤ 90 days); Expiring (≤ 30 days); Overdue (past due date).
- Applies to mains-powered equipment: switches, routers, APs, PDUs, UPS. Not to racks, patch panels or cable managers.
- Org Admin can change interval and thresholds per category.

### 6.10 Versions and concurrency \[v2.2 §7, §4.2\]

- Version history, diff, freeze on approval and change requests as in v2.2.
- Branches can be created, then promoted (replacing the main design) or discarded. No merging.
- LLD records which HLD version it is based on (§5.4). Handover creates an immutable baseline.
- Real-time presence and port-level locking as in v2.2. Where no lock is held, first save wins; the second user sees a conflict warning with the changes and who made them.
- **Undo/redo** persists across autosaves within a session; it resets on explicit "Save version" or page reload. *(Proposed)*

### 6.11 Audit trail and GDPR \[v2.2 §9, §11.5\]

- The audit log is append-only and cannot be edited. Operational CMDB changes are flagged as such.
- Full deletion of an organisation under GDPR removes all its data, including audit logs, within 30 days.

### 6.12 Global search

One search field in the top bar covers: project, country, SAL code, campus, building, floor, room, rack, hostname, serial number, MAC address, asset ID, cable ID and patch-panel port. Results respect the user's role and scope.

## 8. Non-functional requirements, acceptance and inputs

### 8.1 Security and data protection \[v2.2 §11\]

**Launch baseline** (required from the first live use):

- Email and password login with roles and scopes (§4.3); secure password policy; login rate limiting.
- HTTPS everywhere.
- Organisation isolation enforced on the server for every request.
- Daily encrypted backups stored outside the application server, kept at least 30 days, with a tested restore.
- The application refuses to start without its required secrets; no default passwords or keys.
- Data classification, export security and GDPR rules as in v2.2.

**Enterprise requirements** (in place before the first enterprise client goes live; infrastructure paid by Technonex):

- SSO/SAML (Azure AD, Okta, Google Workspace).
- MFA, mandatory for Org Admin, PM and Architect.
- EU hosting; encryption at rest with key rotation.
- Recovery point objective 1 hour; recovery time objective 4 hours.
- Annual penetration test.
